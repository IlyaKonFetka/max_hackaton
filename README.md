# Движок применимости — самопроверка общепита по обязательным требованиям в MAX

Чат-бот + мини-приложение для владельца небольшого заведения общепита. По профилю объекта (7 вопросов) сервис отбирает **только применимые** требования Роспотребнадзора, Роструда и МЧС с привязкой к НПА, показывает, **что не применимо и почему**, проводит самопроверку с фотофиксацией, формирует PDF-акт в чат и превращает нарушения в задачи со сроками и напоминаниями.

Хакатон MAX 2026, трек «Эффективный бизнес». Бот: `@t419_hakaton_max_bot`. Мини-приложение: `https://ilyakonfetka.github.io/max_hackaton/`.

## Назначение

Владелец кафе без юриста и специалиста по охране труда не знает, какие из сотен контрольных вопросов проверочных листов относятся к его точке. Существующие сервисы дают электронные чек-листы и журналы, но не отвечают на вопрос «что применимо именно ко мне». Продукт закрывает этот слой: **профиль объекта → применимые требования разных ведомств → самопроверка → акт → план устранения**.

## Основной пользовательский сценарий

1. `/start` в боте → 7 вопросов кнопками (вид заведения, кухня, производство, места, работники, алкоголь, регион) + название.
2. Бот считает: «применимо 32 требования из 35: Роспотребнадзор — 19, Роструд — 10, МЧС — 3; не применимо 3 — почему».
3. Кнопка **«Открыть самопроверку»** → мини-приложение: список по ведомствам, по каждому пункту «Соблюдается / Нарушение / Не знаю», основание (НПА, пункт, проверочный лист, дата актуальности), комментарий и фото к нарушению. Вкладка **«Не применимо»** — с причиной по каждому пункту. Состояние сохраняется, можно выйти и вернуться.
4. **«Завершить и сформировать акт»** → PDF-акт приходит в чат; каждое нарушение становится задачей со сроком из справочника.
5. `/tasks` → назначить ответственного: контакт сотрудника → кнопка «Отправить сотруднику в MAX» открывает отправку с готовым приглашением (`max.ru/:share`). Открыть задачу по ссылке может только назначенный (по аккаунту MAX или подтверждением номера). Закрытие — с фото «как стало». Бот напоминает за сутки до срока и при просрочке.
6. `/shift` → чек-лист смены по одному пункту: полный текст требования в сообщении, кнопки «Выполнено / Нет / Пропустить»; фото, присланное в этот момент, засчитывается как «выполнено» и привязывается к пункту.

Повторный `/start` показывает статус, а не онбординг.

## Состав и архитектура

```
rules/                    справочник: profile.yaml (поля профиля и вопросы), rospotrebnadzor.yaml, rostrud.yaml, mchs.yaml
backend/app/
  engine/                 движок применимости — чистые функции, ничего не знает о ведомствах
  bot/                    сценарий бота (maxapi, long polling), состояние диалога в БД
  api/                    REST для мини-приложения, валидация initData (HMAC)
  services/               сессии самопроверки, задачи, PDF-акт (reportlab), фото, отправка в чат
  jobs/                   напоминания о сроках и утренний чек-лист
  main.py                 FastAPI + бот + планировщик в одном процессе
miniapp/                  React + Vite + TypeScript + @maxhub/max-ui, MAX Bridge через st.max.ru/js/max-web-app.js
compose.yaml, Dockerfile  один контейнер: бэкенд + бот + собранное мини-приложение на /app/
```

Один процесс Python: FastAPI (API + статика) и бот (long polling к Bot API MAX) + фоновый планировщик. Хранилище — SQLite в томе `/data` (профили, сессии, ответы, задачи, пути к фото). Справочник требований — YAML в репозитории, загружается при старте; версия справочника фиксируется в каждой сессии и в акте.

**Ключевое решение — правила как данные.** Каждое требование в YAML имеет предикат `applies_if` по полям профиля (`all` / `any` / `not` / лист `{field, eq|ne|in|nin|gt|gte|lt|lte}`), реквизиты НПА, периодичность, тип доказательства, срок устранения. Движок при отказе собирает невыполненные листья и переводит их в человеческие фразы («Кухня: нет кухни») — это и есть вкладка «Не применимо». Новая отрасль или ведомство = новый YAML, код не меняется.

**Разделение бот / мини-приложение** — по методичке кейса: последовательные вопросы, статусы, напоминания, короткие регулярные действия — в чате; список из 30 пунктов с фото и возвратом к данным — в мини-приложении. Связка: бот отдаёт `open_app` с `payload=s<id сессии>`, мини-приложение ходит в тот же бэкенд с подписанным `initData`, бэкенд по завершении присылает акт в чат через Bot API.

## Запуск одной командой

```bash
cp .env.example .env        # вписать MAX_BOT_TOKEN
docker compose up --build
```

Поднимается один сервис `app` на `http://localhost:8000`: API, бот (если задан токен), мини-приложение на `http://localhost:8000/app/`, здоровье — `GET /health`. Сборка образа: ~2–3 минуты без учёта загрузки базовых образов (проверяется в CI, job `docker-build`).

Без Docker:

```bash
pip install -r backend/requirements.txt
cd backend && python -m uvicorn app.main:app --port 8000
cd miniapp && npm ci && npm run dev      # мини-приложение на http://localhost:5173
```

## Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `MAX_BOT_TOKEN` | токен бота MAX (обязателен для бота; без него работает только API) | — |
| `MAX_BOT_USERNAME` | ник бота для ссылок `https://max.ru/<bot>?start=…` | `t419_hakaton_max_bot` |
| `PUBLIC_API_URL` | публичный HTTPS-адрес бэкенда (ссылки на фото в акте) | `http://localhost:8000` |
| `CORS_ORIGINS` | origin'ы мини-приложения через запятую | `https://ilyakonfetka.github.io,http://localhost:5173` |
| `DATA_DIR` | каталог данных: SQLite, фото, акты | `./data` (в Docker `/data`) |
| `RULES_DIR` | каталог справочника | `./rules` |
| `TZ_OFFSET_HOURS` | смещение локального времени для сроков | `3` |
| `RUN_BOT` | `1` — запускать бота в процессе, `0` — только API | `1` |
| `DEBUG_AUTH` | `1` — принимать `X-Debug-User` вместо `initData` (только локально) | `0` |
| `PORT` | порт | `8000` |

Адрес API для мини-приложения задаётся в `miniapp/public/config.js` (`window.__APP_CONFIG__.apiUrl`) — без пересборки.

## Порты

- `8000` — API, `/media/` (фото), `/app/` (мини-приложение), `/health`, `/docs` (OpenAPI).
- `5173` — dev-сервер Vite (только локальная разработка).

## Зависимости

Python 3.12: `fastapi`, `uvicorn`, `sqlalchemy`, `pyyaml`, `reportlab`, `httpx`, `maxapi==1.2.2` (официальная библиотека Bot API MAX). Версии зафиксированы в `backend/requirements.txt`.
Node 20: `react 19`, `vite 8`, `typescript 6`, `@maxhub/max-ui 0.5` — `miniapp/package-lock.json`.

> `maxapi` версий ≤ 0.9.x и форк `max-messenger/max-botapi-python` передают токен query-параметром, который API больше не принимает (401). Нужна 1.2.2+.

## Внешние сервисы и интеграции

- **MAX Bot API** (`platform-api2.max.ru`) — сообщения, inline-кнопки (`callback`, `open_app`, `request_contact`, `request_geo_location`), загрузка PDF в чат, команды бота. Long polling — публичный адрес боту не нужен.
- **MAX Bridge** (`st.max.ru/js/max-web-app.js`) — `initData` для авторизации, `HapticFeedback`, `enableClosingConfirmation`; камера — через стандартный `<input type="file" capture>`.
- **GitHub Pages** — хостинг мини-приложения (workflow `.github/workflows/pages.yml`).

Интеграций с ГИС ТОР КНД, реестром обязательных требований и другими государственными системами в MVP нет — см. «Работа с данными».

## Работа с данными

- **Справочник требований подготовлен вручную по опубликованным НПА и является частичным** (35 требований: 20 Роспотребнадзор, 10 Роструд, 4 МЧС + 1 по обороту алкоголя). У каждой записи: документ, пункт, проверочный лист, дата актуальности `as_of` и флаг `verified`. На момент сдачи `verified: false` у всех записей: номера контрольных вопросов проверочных листов и пунктов **СанПиН 2.3/2.4.4282-26** (действует с 01.09.2026, заменил СанПиН 2.3/2.4.3590-20) требуют сверки с официальным текстом. Это отмечается в акте строкой «реквизиты требуют сверки».
- Пользовательские данные (профиль, ответы, фото, задачи) — только в локальной БД и томе `/data`; в MAX ничего кроме сообщений не уходит.
- Фото при сохранении нормализуются (EXIF-ориентация применяется к пикселям, длинная сторона ≤ 1600 px, JPEG) — иначе снимки с телефона попадают в PDF на боку. Хранятся файлами со случайными именами, в БД — путь; отдаются по `/media/`.
- Акт — информационный документ, не декларация соблюдения обязательных требований; дисклеймер печатается в PDF.

## Тестовые данные

Отдельных тестовых учётных записей нет: любой пользователь MAX проходит онбординг за минуту. Для демо два профиля:

- **А — кафе с кухней**: Кафе / ресторан · кухня есть · производство есть · 21–50 мест · 6–15 работников · без алкоголя → 32 применимых, 3 не применимо.
- **Б — кофе навынос**: Кофейня · кухни нет · производства нет · навынос · без работников · без алкоголя → 8 применимых, 27 не применимо (причины: нет кухни, нет работников, нет посадочных мест).

Локально без MAX: `DEBUG_AUTH=1`, заголовок `X-Debug-User: <любое число>`; мини-приложение — `http://localhost:5173/?debug_user=1`.

## Пошаговый сценарий проверки

1. Открыть `@t419_hakaton_max_bot`, `/start`. Ответить на 7 вопросов кнопками (профиль А), ввести название.
2. Нажать «Верно, показать требования». Ожидание: сообщение с числом применимых по ведомствам и кнопки «Открыть самопроверку», «Почему не применимо (3)».
3. Нажать «Почему не применимо» — список неприменимых с причиной.
4. Нажать «Открыть самопроверку». Ожидание: мини-приложение со списком по ведомствам, прогресс 0 из 32.
5. У 2–3 пунктов выбрать «Нарушение», добавить комментарий, приложить фото. Остальные — «Соблюдается» (можно не все). Закрыть и открыть мини-приложение — статусы сохранены.
6. Вкладка «Не применимо» — те же 3 пункта с причинами.
7. «Завершить и сформировать акт». Ожидание: экран итога; в чат приходит сообщение с планом устранения и PDF-акт с профилем, требованиями, статусами, фото, реквизитами НПА и разделом «не применимо».
8. `/tasks` — задачи с датами. «Назначить ответственного» → отправить контакт → бот даёт ссылку `https://max.ru/t419_hakaton_max_bot?start=task_<id>`. «Выполнено» → фото → задача закрыта.
9. `/shift` — пункты по одному; ответ заменяет вопрос и присылает следующий; двойное нажатие — «Уже отмечено»; «Прервать» — итог; повторный `/shift` продолжает с места остановки.
10. `/start` повторно — статус заведения. `/profile` → профиль Б → другой набор требований (демонстрация движка).

## Примеры ожидаемого поведения

- Профиль без кухни не получает пункты про бракераж, поточность, обработку яиц; во вкладке «Не применимо» у них причина «Кухня: нет кухни».
- Профиль без работников не получает ни одного требования Роструда.
- Объект на 21–50 мест не получает требование о плане эвакуации (порог — 50 и более); при выборе «больше 50» — получает.
- Ответ в завершённую сессию → `409`; чужое требование → `400`; запрос без `initData` → `401`.
- Просроченная задача — уведомление владельцу и ответственному один раз, за сутки до срока — напоминание.

## Известные ограничения

- Реквизиты пунктов НПА и номера контрольных вопросов не сверены с официальными текстами (`verified: false`) — это задача редактора справочника, не кода.
- Региональные требования не учитываются: регион собирается, но на отбор не влияет.
- Геолокация в веб-версии MAX недоступна (ограничение клиента) — она необязательна.
- Мини-приложение на GitHub Pages требует публичного HTTPS-адреса бэкенда (`config.js`).
- Один объект на пользователя; повторный онбординг обновляет профиль и закрывает незавершённую самопроверку.
