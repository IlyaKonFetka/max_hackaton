# Движок применимости

Чат-бот и мини-приложение в MAX для владельца небольшого кафе, столовой или магазина у дома. Бот задаёт восемь вопросов о заведении и отбирает из проверочных листов Роспотребнадзора, Роструда и МЧС те требования, которые к нему относятся. По остальным объясняет, почему они не относятся. Дальше владелец проходит самопроверку в мини-приложении, получает PDF-акт в чат, а нарушения становятся задачами со сроками и напоминаниями.

Хакатон MAX 2026, трек «Эффективный бизнес», команда t419.

| Что | Где |
|---|---|
| Бот | `@t419_hakaton_max_bot`, https://max.ru/t419_hakaton_max_bot |
| Мини-приложение | https://ilyakonfetka.github.io/max_hackaton/ (открывается кнопкой в боте) |
| API на сервере проверки | https://185-246-64-221.sslip.io, описание в `openapi.yaml`, интерактивно на `/docs` |
| Проверки API | `DATA-API.yaml` (DATA-API 1.0, проходит валидатор организаторов) |
| Тестовые данные | `testdata/profiles.json` |

## Зачем это нужно

У владельца кафе на 30 мест обычно нет юриста и специалиста по охране труда. Проверочный лист Роспотребнадзора для общепита (приказ № 808, приложение № 2) содержит 124 вопроса, плюс отдельные листы Роструда и МЧС. Часть вопросов к конкретной точке не относится, но какая именно, из текста приказа не понять. С 1 сентября 2026 года к тому же действует новый СанПиН 2.3/2.4.4282-26, а проверочный лист всё ещё ссылается на пункты старого 3590-20.

Сервисы электронных чек-листов (Service Inspector, Haccp-Online, CheckOffice, MD Audit) хорошо ведут журналы, но исходят из того, что пользователь уже знает, что проверять. Здесь закрыт предыдущий шаг: профиль объекта, затем требования разных ведомств, которые к нему применимы, затем самопроверка, акт и план устранения.

## Основной сценарий

1. `/start`: шесть вопросов кнопками (вид заведения, кухня, собственное производство, посадочные места, работники, алкоголь), регион точкой на карте или текстом и название.
2. Бот присылает итог. Для кафе с кухней и 6–15 работниками: применимо 34 требования из 52 (Роспотребнадзор 21, Роструд 10, МЧС 3), не применимо 18. Причины показывает кнопка «Почему не применимо».
3. «Открыть самопроверку» запускает мини-приложение. Требования сгруппированы по ведомствам, у каждого три ответа: «Соблюдается», «Нарушение», «Не знаю». Под пунктом раскрывается основание: документ, пункт, номер вопроса проверочного листа, дата сверки. К нарушению можно приложить фото и комментарий. Ответы сохраняются сразу, мини-приложение можно закрыть и открыть позже.
4. «Завершить и сформировать акт»: в чат приходит PDF-акт, каждое нарушение становится задачей со сроком из справочника.
5. `/tasks`: владелец назначает ответственного. Он отправляет боту контакт сотрудника, бот даёт кнопку «Отправить сотруднику в MAX», которая открывает отправку с готовым приглашением (`max.ru/:share`). Сотрудник закрывает задачу с фото «как стало». Напоминание приходит за сутки до срока, ещё одно — при просрочке.
6. `/shift`: короткий чек-лист смены из требований с периодичностью «каждую смену». Пункты приходят по одному, фото вместо ответа засчитывается как «выполнено» и привязывается к пункту.

Повторный `/start` показывает состояние заведения, а не начинает онбординг заново.

Роли две. Владелец заполнил профиль, ему доступны самопроверка, акт, назначения и `/team`. Сотрудник попадает в команду через `/team` или принимает задачу по ссылке. Он видит свои задачи и чек-лист смены, но не может переназначать задачи и менять профиль. Ссылки-приглашения именные: бот сверяет аккаунт MAX, а если известен только телефон, просит сотрудника прислать свой контакт.

## Архитектура

```
rules/                    справочник: profile.yaml (вопросы профиля), rospotrebnadzor.yaml (общепит),
                          retail.yaml (магазин у дома), rostrud.yaml, mchs.yaml
testdata/profiles.json    демо-профили и ожидаемые результаты движка
backend/app/
  engine/                 движок применимости: чистые функции, про ведомства ничего не знает
  bot/                    сценарий бота (maxapi, long polling), состояние диалога хранится в БД
  api/                    REST для мини-приложения, проверка подписи initData
  services/               самопроверки, задачи, роли, PDF-акт (reportlab), фото, геокодирование
  jobs/                   напоминания о сроках и утренний чек-лист
  main.py                 FastAPI, бот и планировщик в одном процессе
miniapp/                  React 19, Vite, TypeScript, @maxhub/max-ui; MAX Bridge из st.max.ru/js/max-web-app.js
deploy/                   Caddyfile сервера проверки, выгрузка openapi.yaml
compose.yaml, Dockerfile  один контейнер: бэкенд, бот и собранное мини-приложение на /app/
```

Бэкенд работает одним процессом Python: FastAPI отдаёт API и статику, рядом крутятся long polling к Bot API MAX и планировщик напоминаний. Данные лежат в SQLite в томе `/data`: профили, самопроверки, ответы, задачи, пути к фото. Справочник хранится в YAML в репозитории и загружается при старте. Его версия записывается в каждую самопроверку и печатается в акте.

Правила живут в данных, а не в коде. У каждого требования в YAML есть условие `applies_if` по полям профиля: узлы `all`, `any`, `not` и сравнения `eq`, `ne`, `in`, `nin`, `gt`, `gte`, `lt`, `lte`. Там же реквизиты НПА, периодичность, тип доказательства и срок устранения. Для неприменимого пункта движок собирает невыполненные условия и переводит их в фразы вроде «Кухня: нет кухни». Магазин у дома добавлен именно так: новый файл `rules/retail.yaml` и один вариант ответа в профиле, код движка не менялся.

Бот и мини-приложение поделены по подсказке из кейса. Последовательные вопросы, статусы, напоминания и короткие регулярные действия идут в чате, список из 30 с лишним пунктов с фото вынесен в мини-приложение. Бот открывает его кнопкой `open_app` с `payload=s<id самопроверки>`, мини-приложение ходит в тот же бэкенд с подписанным `initData`, а по завершении бэкенд присылает акт в чат через Bot API.

## Запуск одной командой

```bash
cp .env.example .env        # вписать MAX_BOT_TOKEN
docker compose up --build
```

Поднимается сервис `app` на `http://localhost:8000`: API, бот (если задан токен) и мини-приложение на `http://localhost:8000/app/`. Проверка живости: `GET /health`. Образ собирается примерно за 20 секунд в CI (job `docker-build`) и за минуту на сервере с 1 ГБ памяти.

> Рабочий экземпляр бота уже запущен на сервере проверки. Если запустить второй с тем же токеном и `RUN_BOT=1`, два процесса начнут делить входящие сообщения. Для локальной проверки API и мини-приложения ставьте `RUN_BOT=0`.

Без Docker:

```bash
pip install -r backend/requirements.txt
cd backend && python -m uvicorn app.main:app --port 8000
cd miniapp && npm ci && npm run dev      # мини-приложение на http://localhost:5173
```

## Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `MAX_BOT_TOKEN` | токен бота MAX; без него работает только API | нет |
| `MAX_BOT_USERNAME` | ник бота для ссылок `https://max.ru/<bot>?start=…` | `t419_hakaton_max_bot` |
| `PUBLIC_API_URL` | публичный HTTPS-адрес бэкенда, из него строятся ссылки на фото | `http://localhost:8000` |
| `CORS_ORIGINS` | адреса мини-приложения через запятую | `https://ilyakonfetka.github.io,http://localhost:5173` |
| `DATA_DIR` | каталог данных: SQLite, фото, акты | `./data` (в Docker `/data`) |
| `RULES_DIR` | каталог справочника | `./rules` |
| `TZ_OFFSET_HOURS` | смещение местного времени для сроков и напоминаний | `3` |
| `RUN_BOT` | `1` запускает бота в процессе, `0` оставляет только API | `1` |
| `API_TEST_KEYS` | ключи доступа к API без MAX для автоматической проверки, формат `ключ:user_id,…` | пусто |
| `DEBUG_AUTH` | `1` принимает заголовок `X-Debug-User` вместо `initData`, только для локальной разработки | `0` |
| `PORT` | порт | `8000` |

Адрес API для мини-приложения задан в `miniapp/public/config.js` (`window.__APP_CONFIG__.apiUrl`). Файл отдаётся как есть, пересобирать ничего не нужно.

- `8000`: API, `/media/` (фото), `/app/` (мини-приложение), `/health`, `/docs`.

## Зависимости

Python 3.12: `fastapi`, `uvicorn`, `sqlalchemy`, `pyyaml`, `reportlab`, `pillow`, `httpx`, `maxapi==1.2.2`. Версии зафиксированы в `backend/requirements.txt`, для тестов `backend/requirements-dev.txt`.
Node 20: `react 19`, `vite 8`, `typescript 6`, `@maxhub/max-ui 0.5`, версии в `miniapp/package-lock.json`.

`maxapi` версий 0.9.x и форк `max-messenger/max-botapi-python` передают токен query-параметром, а API MAX такой запрос отклоняет с 401. Поэтому нужна 1.2.2 или новее.

## Внешние сервисы

- MAX Bot API (`platform-api2.max.ru`): сообщения, кнопки `callback`, `open_app`, `request_contact`, `request_geo_location`, загрузка PDF в чат, команды бота. Бот работает через long polling, публичный адрес ему не нужен.
- MAX Bridge (`st.max.ru/js/max-web-app.js`): `initData` для входа в мини-приложение, `HapticFeedback`, подтверждение закрытия окна. Камера открывается обычным `<input type="file" capture>`.
- Nominatim (OpenStreetMap): регион по точке на карте. Один запрос на онбординг; если сервис не ответил, регион сохраняется координатами.
- GitHub Pages: хостинг мини-приложения, сборка в `.github/workflows/pages.yml`.
- Сервер проверки: VDS на Ubuntu 24.04 (1 vCPU, 1 ГБ). На нём `docker compose up -d` из этого репозитория и Caddy (`deploy/Caddyfile`) с сертификатом Let's Encrypt. Домен `185-246-64-221.sslip.io` даёт публичный DNS-сервис sslip.io, в имени зашит IP сервера. ngrok не подошёл: он не пускает агентов с российских IP дата-центров (`ERR_NGROK_9040`).

Интеграций с ГИС ТОР КНД, реестром обязательных требований и другими государственными системами в MVP нет. Справочник собран вручную, подробности в разделе «Работа с данными».

## Собственный API

Через этот REST работает мини-приложение. Спецификация лежит в `openapi.yaml` (OpenAPI 3.1, выгружается из кода командой `RUN_BOT=0 python deploy/export_openapi.py`), обязательные проверки в `DATA-API.yaml`.

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/health` | открыт | жив ли сервис, сколько требований, версия справочника |
| GET | `/api/rules` | открыт | поля профиля и требования с реквизитами НПА |
| POST | `/api/applicability` | открыт | движок: по профилю возвращает применимые требования и причины для остальных |
| PUT | `/api/venue` | user | профиль заведения, то же, что онбординг в боте |
| GET | `/api/me` | user | профиль, текущая самопроверка, число задач |
| GET | `/api/session` | user | текущая самопроверка или указанная через `?id=` |
| POST | `/api/session/new` | user | новая самопроверка |
| PUT | `/api/session/{sessionId}/answers/{ruleId}` | user | ответ по пункту (`ok`, `violation`, `unknown`) и комментарий |
| POST | `/api/session/{sessionId}/answers/{ruleId}/photo` | user | фото к пункту, multipart |
| POST | `/api/session/{sessionId}/finish` | user | завершение: нарушения становятся задачами, акт уходит в чат |
| GET | `/api/tasks` | user | открытые задачи: у владельца свои, у сотрудника назначенные ему |
| POST | `/api/tasks/{taskId}/done` | user | закрыть задачу, фото по желанию (multipart) |

Роль `user` в мини-приложении подтверждается заголовком `X-Max-Init-Data`: сервер проверяет подпись initData (HMAC-SHA256 от токена бота). Платформа автоматической проверки такую подпись сделать не может, поэтому для неё есть заголовок `X-Api-Key: <ключ>` или `Authorization: Bearer <ключ>`. Ключи задаются в `API_TEST_KEYS`, каждый даёт права одного тестового пользователя, реального пользователя MAX через ключ подделать нельзя. Ключ для проверки указан на служебном слайде презентации. У тестового пользователя нет диалога с ботом, поэтому акт для него собирается, но в чат не уходит.

## Работа с данными

Справочник собран вручную по первоисточникам и сверен с их текстом 20.09.2026. Всего 52 требования: Роспотребнадзор 24 для общепита и 14 для розницы, Роструд 10, МЧС 4. У каждого указаны документ, пункт, номер вопроса проверочного листа и дата сверки `as_of`; флаг `verified: true` стоит у 51.

- Общепит: СанПиН 2.3/2.4.4282-26 (действует с 01.09.2026, пункты пронумерованы сквозь весь документ) и проверочный лист из приказа Роспотребнадзора от 24.12.2021 № 808, приложение № 2. Лист ссылается на пункты утратившего силу СанПиН 3590-20, поэтому в справочнике указаны оба реквизита. Что поменялось в новом СанПиН и как это учтено, написано в шапке `rules/rospotrebnadzor.yaml`: бракераж и суточные пробы остались только для организованных коллективов, отдельного пункта про обработку яиц нет, ежемесячная генеральная уборка больше не нормируется.
- Розница: СП 2.3.6.3668-20 и приложение № 1 того же приказа (176 вопросов), файл `rules/retail.yaml`.
- Роструд: ТК РФ и приказ Роструда № 20. Номера приложений-листов сверены по оглавлению, номера вопросов внутри листов нет.
- МЧС: Правила противопожарного режима (ПП РФ № 1479).
- Не сверены пункты Правил оказания услуг общественного питания (ПП № 1515) в требовании `rpn-consumer-info`. Там стоит `verified: false`, в акте напечатано «реквизиты требуют сверки».

Профиль, ответы, фото и задачи хранятся только в базе и томе `/data` на сервере. В MAX уходят только сообщения бота.

Фото при сохранении поворачиваются по EXIF, ужимаются до 1600 px по длинной стороне и перекодируются в JPEG. Без поворота снимки с телефона попадали в PDF на боку. Файлы хранятся под случайными именами, в базе только путь, раздаются по `/media/`.

Акт носит информационный характер и не заменяет декларацию соблюдения обязательных требований. Эта оговорка напечатана в PDF.

## Тестовые данные

Отдельные учётные записи для бота не нужны: любой пользователь MAX проходит онбординг примерно за минуту. Демо-профили и ожидаемые результаты лежат в `testdata/profiles.json`, тест `test_testdata_profiles_match_engine` сверяет их с движком.

| Профиль | Применимо | По ведомствам | Не применимо |
|---|---|---|---|
| Кафе: кухня, производство, 21–50 мест, 6–15 работников, без алкоголя | 34 | РПН 21, Роструд 10, МЧС 3 | 18 |
| Кофе навынос: без кухни, мест и работников | 10 | РПН 8, МЧС 2 | 42 |
| Столовая: кухня, больше 50 мест, 6–15 работников | 37 | РПН 23, Роструд 10, МЧС 4 | 15 |
| Магазин у дома: без кухни, 1–5 работников, с алкоголем | 27 | РПН 15, Роструд 9, МЧС 3 | 25 |

Проверка API без MAX: `API_TEST_KEYS=<ключ>:900000001` и заголовок `X-Api-Key: <ключ>`. Сценарий из `DATA-API.yaml` проходит от профиля до закрытия задачи. Для разработки мини-приложения в браузере есть `DEBUG_AUTH=1` и адрес `http://localhost:5173/?debug_user=1`, только локально.

## Как проверить по шагам

1. Открыть `@t419_hakaton_max_bot`, отправить `/start`. Ответить кнопками как в профиле «Кафе», регион отправить точкой на карте (в веб-версии MAX геолокации нет, регион можно написать), ввести название.
2. Нажать «Верно, показать требования». Придёт итог: 34 применимых по ведомствам и кнопки «Открыть самопроверку» и «Почему не применимо (18)».
3. «Почему не применимо»: 18 пунктов, сгруппированных по причине.
4. «Открыть самопроверку»: список по ведомствам, прогресс «0 из 34».
5. Отметить 2–3 пункта как «Нарушение», добавить комментарий и фото, остальные как «Соблюдается» (можно не все). Закрыть и снова открыть мини-приложение: ответы на месте.
6. Вкладка «Не применимо»: те же 18 пунктов с причинами.
7. «Завершить и сформировать акт». Мини-приложение покажет итог, в чат придёт план устранения и PDF-акт с профилем, требованиями, статусами, фото и реквизитами НПА.
8. `/tasks`: задачи со сроками. «Назначить ответственного», отправить контакт, нажать «Отправить сотруднику в MAX». Затем «Выполнено», фото, задача закрыта.
9. `/shift`: пункты приходят по одному, ответ заменяет вопрос и присылает следующий. Повторное нажатие даёт «Уже отмечено», «Прервать» показывает итог, повторный `/shift` продолжает с того же места.
10. `/start` показывает состояние заведения. `/profile` с ответами «Кофе навынос» даёт 10 требований вместо 34.

## Ожидаемое поведение

- Профиль без кухни не получает поточность, ХАССП и технологические карты, у них причина «Кухня: нет кухни».
- Бракераж и суточные пробы появляются только у столовой: по СанПиН 4282-26 это требования к питанию организованных коллективов.
- Магазин получает розничный справочник (термометры и журнал температуры, товарное соседство, санодежда) и ни одного требования СанПиН по общепиту.
- Без работников нет ни одного требования Роструда.
- План эвакуации появляется от 50 посадочных мест, при 21–50 его нет.
- API: ответ в завершённую самопроверку даёт `409`, чужое требование `400`, запрос без авторизации `401`, неизвестный вид заведения `422`.
- Просроченная задача: одно уведомление владельцу и ответственному. За сутки до срока приходит напоминание.

## Известные ограничения

- Региональные требования не учитываются: регион сохраняется и печатается в акте, но на отбор не влияет.
- Номера вопросов внутри листов Роструда и МЧС не сверены, в справочнике указаны номера приложений и пункты НПА.
- Геолокации нет в веб-версии MAX, там регион вводится текстом.
- У пользователя одно заведение. Повторный онбординг обновляет профиль и закрывает незавершённую самопроверку.
- Мини-приложение на GitHub Pages берёт адрес API из `config.js`, при переезде сервера его нужно поправить.

## Остановка и повторный запуск

```bash
docker compose down          # остановить, данные остаются в томе app-data
docker compose up -d         # запустить снова
docker compose down -v       # остановить и удалить данные
```
